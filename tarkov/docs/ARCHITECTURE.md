# Архитектура DEV0.1

`JSON mapgen / furniture -> preload callbacks -> main -> lifecycle -> BN adapter -> engine`

## Ответственность

| Часть | Владеет |
|---|---|
| JSON | Геометрия, обстановка, фиксированная тестовая добыча, станции входа/выхода |
| preload.lua | Регистрация событий и действий осмотра |
| main.lua | Связывание UI/событий с логикой, сообщения, таймер |
| trkv_lifecycle.lua | Состояния и однократный учёт результата |
| trkv_bn.lua | Переходы, проверка измерения, потеря вещей и очистка |
| BN | Реальные предметы, карта, HP, Lua storage и сохранения |

## Состояния

`home -> entering -> active -> returning -> cleanup -> home`

- Новая попытка входа разрешена в `home` и в нашем убежище. Незавершённая
  `entering` в убежище повторяется через терминал с тем же sequence.
- Отказ перехода не даёт победу и не отбирает вещи в убежище.
- Неудавшийся вход остаётся `entering`: целевое измерение могло ещё не появиться,
  поэтому очистку не вызываем. Загрузка оставляет персонажа в убежище до ручного
  повтора через терминал. `entry_duration` сохраняет выбранную длительность; перед
  повтором входа дедлайн ставится от текущего времени. Состояние `entering` уже
  внутри рейда восстанавливается в active с прежним дедлайном — без его продления.
- Для старого checkpoint cleanup/entry_failed в убежище recover включает тот же
  повтор. При отсутствии entry_duration длительность берётся из меню нового повтора.
  Настоящие checkpoint после сыгранного рейда по-прежнему требуют очистки.
- Поражение окончательно; запрос эвакуации до фактического возвращения может перейти
  в поражение при смерти или таймауте. Повтор не выдаёт дополнительный результат.
- Штраф применяется однократно до выхода из рейдового измерения.
- Очистка разрешена только из убежища, после выхода из временной территории.
- `sequence` идентифицирует попытку, `settled` защищает от повторного учёта.
- Периодические проверки не создают новый дедлайн при загрузке.
- Предупреждения за 5 минут и за 1 минуту используют тот же абсолютный дедлайн.
  time_warning хранит достигнутую стадию в простых данных; новая попытка/повтор
  не начавшегося входа сбрасывает её. Загрузка уже сохранённой отметки не повторяет
  предупреждение. Загрузка более старого сохранения до предупреждения может его
  показать снова; ради сообщения отдельное сохранение не выполняется.
- Несоответствие активного состояния и текущего измерения блокирует автоматические изменения.
- Это ограничение действует и при сохранённом состоянии возврата.

## Почему reset, а не delete

BN сохраняет игру перед очисткой. `reset_dimension` оставляет метаданные измерения,
поэтому checkpoint `cleanup` можно обработать ещё раз после загрузки. Полное удаление
потребовало бы дополнительно распознавать уже отсутствующее измерение.
Сгенерированные данные удаляются; раскладка и границы сохраняются для следующего входа.

## Тип пространства

Оба измерения используют собственный `trkv_raid_space` с `save_prefix: trkv_dev01_`.
Метаданные измерений сохраняются вместе с персонажем. При отсутствии записи
для текущего измерения BN восстанавливает `dimension_info.world_type` по префиксу ID. Обычный `pocket_dimension` имеет префикс `pocket_` и не
соответствует нашим именам. Границы и правила перемещения собственного типа совпадают
со штатным карманным пространством. Проверка этого контракта входит в fast-checks;
холодная загрузка типа и границ также прошла отдельный native-сценарий.

## Сохранения

В `game.mod_storage["trkv_raid_core"].raid` только строки, числа и bool.
Не сохранять туда Item/Npc/Map, функции, указатели или временные ссылки.
Сами предметы сохраняет BN, мы не пересоздаём оружие по ID.
BN десериализует вложенные таблицы в новые объекты. Обработчики каждый раз получают
актуальную `storage.raid`, а не захватывают таблицу, созданную до загрузки.
Повторный вызов обработчика загрузки не должен удваивать результат рейда.
В этой базе `game::load` блокирует запись до завершения загрузки. Поэтому load hooks
только ставят флаг восстановления; первый последующий игровой тик вызывает `recover`.
Это позволяет переходу/сбросу выполнить своё обязательное внутреннее сохранение.

Активный рейд и cleanup проверены в новых процессах после полного завершения
предыдущего процесса. Reader вызывает штатный load(world_name), получает новый Lua
state после setup, затем проверяет первый post-load tick и однократный результат.
Для восстановления границ требуется production-патч 0001: до load_map буфер m ещё
связан с прежним измерением; pocket_info нужно применять к буферу сохранённого ID.

Ограничение: произвольные исключения и обрывы внутри любой операции движка этим
не покрываются. Не выдавать replay состояния за полную транзакционность всех действий.

## Зависимости следующих систем

| Система | Обязательная основа |
|---|---|
| Контроллер НПС | Проверенный цикл и очистка участников |
| Полноценная карта | Ограничения движения, видимости и боя |
| Экономика | Проверенная сохранность/потеря предметов |
| Квесты | ID рейда и устойчивые ID целей, отдельное подтверждение событий |
| Страхование | Идентичность вещей, их судьба и окончательный результат |
| Улучшения базы | Расход ресурсов, проверка размещения, восстановление при ошибке |
| Боссы | Общая групповая логика, роли, охрана цели |

## Направление самостоятельной игры

С 21.10.2026 продукт — самостоятельная конверсия BN. Дерево выше описывает
действующий рейдовый модуль, который остаётся внутренней частью игры.
Будущий профиль содержит независимые ID издания и стороны ЧВК, с версией
схемы и однократным стартовым комплектом. Профиль не входит в состояние одной
попытки raid и не сбрасывается при эвакуации/поражении. Сам профиль и новый экран
создания ещё не реализованы. Навыки и зависимости движка описаны в BUILD_STRATEGY.md.

Порядок выбора — издание → сторона ЧВК. Используются переработанные существующие
экраны scenario/profession, без нового экрана с нуля. Эта работа отложена до своего
этапа; ближайшим слоем после рейдового фундамента остаётся основа противников.

## Реестр участников второго слоя

trkv_participants хранит записи по числовому character_id BN, преобразованному в
строковый ключ. Поля записи: id, side, squad, patrol. Маршрут копируется по явному
списку x/y/z; ни Npc, ни дополнительные поля исходного объекта в сохранение не
попадают. Сторона и отряд независимы: одинаковая сторона сама по себе не задаёт
дружбу, одинаковое имя отряда не задаёт отношения между разными рейдами. Правила
дипломатии и экран выбора ЧВК этим модулем не вводятся.

begin с тем же активным sequence сохраняет записи; новый sequence очищает реестр.
Устаревший sequence, повторный ID и попытка открыть уже закрытый рейд отклоняются.
find доступен только для активного текущего рейда в его измерении. finish вызывается
после успешной очистки движком; неуспешный возврат не должен удалять записи.

main подключает реестр к api.enter и api.cleanup. Перед входом открывается реестр
текущего sequence, чтобы внутреннее сохранение движка уже видело его метаданные.
Закрытие выполняется только после успешного reset_dimension. Поэтому эвакуация,
поражение, таймаут и восстановление cleanup используют один путь. При отказе
возврата/очистки записи сохраняются; повтор ожидающего входа не создаёт новый реестр.

Восстановление после загрузки разрешает старым сохранениям без реестра получить
пустую таблицу текущего рейда. Это не создаёт НПС и не восстанавливает их по шаблону.
Обе вложенные таблицы storage.raid и storage.participants разрешаются заново при
каждом обращении. В load hooks по-прежнему только флаг; восстановление идёт на тике.

NPC-probe регистрирует настоящий ID и получает собственный маршрут в lua_ai,
но больше не открывает и не закрывает реестр самостоятельно. Базовый рейд остаётся
пустым; отдельный выбор патрульного рейда подключает создание участников.

## Создание группы участников

trkv_deployment.ensure принимает manifest со стабильными slot, side, squad и
маршрутом, а также адаптер создания/поиска актёров. participants.slots хранит
состояние creating/ready и выданный ID. Повтор ensure и загрузка не пересоздают
готовое место, даже если участник погиб или его запись удалена. Новый sequence
открывает новый набор мест; завершение очищает actors и slots вместе.

Перед вызовом движка место помечается creating. После прерывания допускается
привязать ровно одного актёра с маркерами sequence/slot и сохранить уже пройденный
маршрут зарегистрированного участника. Нулевой/неоднозначный результат останавливает
создание без повторного spawn; полной транзакционности движка модуль не обещает.

Первый native-probe предоставлял адаптер через spawn_npc тестового драйвера и
маркировал настоящих НПС Creature values. Этот групповой опыт прошёл на двух ОС.

trkv_encounter теперь предоставляет игровой адаптер через gapi.spawn_npc_at из
патча 0002. API отклоняет неизвестный шаблон, непроходимую/занятую клетку и место
вне bubble; после создания вызывает load_npcs, чтобы участник был активен сразу.
Собственные TRKV_PATROL/trkv_patrol_tester используют нейтральную тестовую фракцию.

mod.depart сохраняет выбранный encounter до входа. Повтор неудавшегося входа
сохраняет исходный режим. Создание идёт после успешного входа либо на post-load
тике; encounter_deployed предотвращает повтор, а slots защищают промежуточные
состояния. Обработчик TRKV_PATROL каждый раз ищет запись по текущему actor ID.
Новый игровой путь проверяется отдельно от уже пройденного тестового адаптера.
