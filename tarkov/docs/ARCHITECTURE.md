# Архитектура DEV0.1

`JSON mapgen / furniture -> preload callbacks -> main -> lifecycle -> BN adapter -> engine`

## Ответственность

| Часть | Владеет |
|---|---|
| JSON | Геометрия, обстановка, фиксированная тестовая добыча, станции входа/выхода |
| preload.lua | Регистрация событий и действий осмотра |
| main.lua | Связывание UI/событий с логикой, сообщения, таймер |
| trkv_lifecycle.lua | Состояния и однократный учёт результата |
| trkv_bn.lua | Переходы, проверка измерения, потеря вещей и очистка |
| BN | Реальные предметы, карта, HP, Lua storage и сохранения |

## Состояния

`home -> entering -> active -> returning -> cleanup -> home`

- Новая попытка входа разрешена в `home` и в нашем убежище. Незавершённая
  `entering` в убежище повторяется через терминал с тем же sequence.
- Отказ перехода не даёт победу и не отбирает вещи в убежище.
- Неудавшийся вход остаётся `entering`: целевое измерение могло ещё не появиться,
  поэтому очистку не вызываем. Загрузка оставляет персонажа в убежище до ручного
  повтора через терминал. `entry_duration` сохраняет выбранную длительность; перед
  повтором входа дедлайн ставится от текущего времени. Состояние `entering` уже
  внутри рейда восстанавливается в active с прежним дедлайном — без его продления.
- Для старого checkpoint cleanup/entry_failed в убежище recover включает тот же
  повтор. При отсутствии entry_duration длительность берётся из меню нового повтора.
  Настоящие checkpoint после сыгранного рейда по-прежнему требуют очистки.
- Поражение окончательно; запрос эвакуации до фактического возвращения может перейти
  в поражение при смерти или таймауте. Повтор не выдаёт дополнительный результат.
- Штраф применяется однократно до выхода из рейдового измерения.
- Очистка разрешена только из убежища, после выхода из временной территории.
- `sequence` идентифицирует попытку, `settled` защищает от повторного учёта.
- Периодические проверки не создают новый дедлайн при загрузке.
- Предупреждения за 5 минут и за 1 минуту используют тот же абсолютный дедлайн.
  time_warning хранит достигнутую стадию в простых данных; новая попытка/повтор
  не начавшегося входа сбрасывает её. Загрузка уже сохранённой отметки не повторяет
  предупреждение. Загрузка более старого сохранения до предупреждения может его
  показать снова; ради сообщения отдельное сохранение не выполняется.
- Несоответствие активного состояния и текущего измерения блокирует автоматические изменения.
- Это ограничение действует и при сохранённом состоянии возврата.

## Почему reset, а не delete

BN сохраняет игру перед очисткой. `reset_dimension` оставляет метаданные измерения,
поэтому checkpoint `cleanup` можно обработать ещё раз после загрузки. Полное удаление
потребовало бы дополнительно распознавать уже отсутствующее измерение.
Сгенерированные данные удаляются; раскладка и границы сохраняются для следующего входа.

## Тип пространства

Оба измерения используют собственный `trkv_raid_space` с `save_prefix: trkv_dev01_`.
Метаданные измерений сохраняются вместе с персонажем. При отсутствии записи
для текущего измерения BN восстанавливает `dimension_info.world_type` по префиксу ID. Обычный `pocket_dimension` имеет префикс `pocket_` и не
соответствует нашим именам. Границы и правила перемещения собственного типа совпадают
со штатным карманным пространством. Проверка этого контракта входит в fast-checks;
холодная загрузка типа и границ также прошла отдельный native-сценарий.

## Сохранения

В `game.mod_storage["trkv_raid_core"].raid` только строки, числа и bool.
Не сохранять туда Item/Npc/Map, функции, указатели или временные ссылки.
Сами предметы сохраняет BN, мы не пересоздаём оружие по ID.
BN десериализует вложенные таблицы в новые объекты. Обработчики каждый раз получают
актуальную `storage.raid`, а не захватывают таблицу, созданную до загрузки.
Повторный вызов обработчика загрузки не должен удваивать результат рейда.
В этой базе `game::load` блокирует запись до завершения загрузки. Поэтому load hooks
только ставят флаг восстановления; первый последующий игровой тик вызывает `recover`.
Это позволяет переходу/сбросу выполнить своё обязательное внутреннее сохранение.

Активный рейд и cleanup проверены в новых процессах после полного завершения
предыдущего процесса. Reader вызывает штатный load(world_name), получает новый Lua
state после setup, затем проверяет первый post-load tick и однократный результат.
Для восстановления границ требуется production-патч 0001: до load_map буфер m ещё
связан с прежним измерением; pocket_info нужно применять к буферу сохранённого ID.

Ограничение: произвольные исключения и обрывы внутри любой операции движка этим
не покрываются. Не выдавать replay состояния за полную транзакционность всех действий.

## Зависимости следующих систем

| Система | Обязательная основа |
|---|---|
| Контроллер НПС | Проверенный цикл и очистка участников |
| Полноценная карта | Ограничения движения, видимости и боя |
| Экономика | Проверенная сохранность/потеря предметов |
| Квесты | ID рейда и устойчивые ID целей, отдельное подтверждение событий |
| Страхование | Идентичность вещей, их судьба и окончательный результат |
| Улучшения базы | Расход ресурсов, проверка размещения, восстановление при ошибке |
| Боссы | Общая групповая логика, роли, охрана цели |

## Направление самостоятельной игры

С 21.10.2026 продукт — самостоятельная конверсия BN. Дерево выше описывает
действующий рейдовый модуль, который остаётся внутренней частью игры.
Будущий профиль содержит независимые ID издания и стороны ЧВК, с версией
схемы и однократным стартовым комплектом. Профиль не входит в состояние одной
попытки raid и не сбрасывается при эвакуации/поражении. Сам профиль и новый экран
создания ещё не реализованы. Навыки и зависимости движка описаны в BUILD_STRATEGY.md.

Порядок выбора — издание → сторона ЧВК. Используются переработанные существующие
экраны scenario/profession, без нового экрана с нуля. Эта работа отложена до своего
этапа; ближайшим слоем после рейдового фундамента остаётся основа противников.

## Реестр участников второго слоя

trkv_participants хранит записи по числовому character_id BN, преобразованному в
строковый ключ. Поля записи: id, side, squad, patrol. Маршрут копируется по явному
списку x/y/z; ни Npc, ни дополнительные поля исходного объекта в сохранение не
попадают. Сторона и отряд независимы: одинаковая сторона сама по себе не задаёт
дружбу, одинаковое имя отряда не задаёт отношения между разными рейдами. Правила
дипломатии и экран выбора ЧВК этим модулем не вводятся.

begin с тем же активным sequence сохраняет записи; новый sequence очищает реестр.
Устаревший sequence, повторный ID и попытка открыть уже закрытый рейд отклоняются.
find доступен только для активного текущего рейда в его измерении. finish вызывается
после успешной очистки движком; неуспешный возврат не должен удалять записи.

main подключает реестр к api.enter и api.cleanup. Перед входом открывается реестр
текущего sequence, чтобы внутреннее сохранение движка уже видело его метаданные.
Закрытие выполняется только после успешного reset_dimension. Поэтому эвакуация,
поражение, таймаут и восстановление cleanup используют один путь. При отказе
возврата/очистки записи сохраняются; повтор ожидающего входа не создаёт новый реестр.

Восстановление после загрузки разрешает старым сохранениям без реестра получить
пустую таблицу текущего рейда. Это не создаёт НПС и не восстанавливает их по шаблону.
Обе вложенные таблицы storage.raid и storage.participants разрешаются заново при
каждом обращении. В load hooks по-прежнему только флаг; восстановление идёт на тике.

NPC-probe регистрирует настоящий ID и получает собственный маршрут в lua_ai,
но больше не открывает и не закрывает реестр самостоятельно. Базовый рейд остаётся
пустым; отдельный выбор патрульного рейда подключает создание участников.

## Создание группы участников

trkv_deployment.ensure принимает manifest со стабильными slot, side, squad и
маршрутом, а также адаптер создания/поиска актёров. participants.slots хранит
состояние reserved/creating/ready и выданный ID. Повтор ensure и загрузка не пересоздают
готовое место, даже если участник погиб или его запись удалена. Новый sequence
открывает новый набор мест; завершение очищает actors и slots вместе.

Перед вызовом движка место помечается creating. После прерывания допускается
привязать ровно одного актёра с маркерами sequence/slot и сохранить уже пройденный
маршрут зарегистрированного участника. Нулевой/неоднозначный результат останавливает
создание без повторного spawn; полной транзакционности движка модуль не обещает.

Первый native-probe предоставлял адаптер через spawn_npc тестового драйвера и
маркировал настоящих НПС Creature values. Этот групповой опыт прошёл на двух ОС.

trkv_encounter теперь предоставляет игровой адаптер через gapi.spawn_npc_at из
патча 0002. API отклоняет неизвестный шаблон, непроходимую/занятую клетку и место
вне bubble; после создания вызывает load_npcs, чтобы участник был активен сразу.
Собственные TRKV_PATROL/trkv_patrol_tester используют нейтральную тестовую фракцию.

mod.depart сохраняет выбранный encounter до входа. Повтор неудавшегося входа
сохраняет исходный режим. Создание идёт после успешного входа либо на post-load
тике; encounter_deployed предотвращает повтор, а slots защищают промежуточные
состояния. Обработчик TRKV_PATROL каждый раз ищет запись по текущему actor ID.
Новый игровой путь проверяется отдельно от уже пройденного тестового адаптера.

## Переход к удалённой точке патруля

Патч 0003 добавляет Npc.move_towards. Он очищает временный путь, проверяет этаж и
доступность цели, строит путь BN без разрушения и выполняет один соседний шаг через
обычный move_to(..., true). Открытие двери тратит ходы и оставляет НПС на прежней
клетке до следующего решения. Межэтажные цели и непроходимые цели отклоняются.
Сохранение содержит только waypoint/index; временный путь строится заново.

Игровой manifest теперь задаёт патрулям отрезки длиной четыре клетки. Каждый
актёр сохраняет текущую конечную точку до прибытия. Для технической площадки путь
перестраивается на каждом решении; оптимизация длинных маршрутов пока не вводится.
Недопустимая цель (стена или другой этаж) отклоняется без расхода ходов. Если
проходимая цель временно недоступна, участник тратит 100 очков движения на ожидание
и сохраняет выбранную точку вместо передачи управления ванильному блужданию.
Штатный поиск пути уже учитывает занятые клетки через get_legacy_path_avoid.
Дополнительная проверка следующего шага не допускает выталкивания другого НПС,
в том числе когда занята сама конечная точка, которую поиск пути может разрешать.

В save остаются прежние маршрут и индекс: отдельного состояния ожидания нет,
после загрузки занятость проверяется заново. Native-проверка добавляет встречные
маршруты на открытом участке и освобождение занятой цели после сохранения/загрузки.
Узкий коридор без места для обхода пока может вызвать взаимное ожидание: диспетчер
приоритетов, движение назад до кармана и разрешение групповых заторов ещё не сделаны.


## Отдельный боевой режим второго слоя

encounter.ensure принимает режим patrol/combat (по умолчанию patrol для прежних
вызовов). Каждый режим использует свой manifest и production-шаблон, но общий
реестр, ready-slots, восстановление и очистку. Неизвестный режим отклоняется.
main сохраняет выбранный режим до перехода, передаёт его при deployment и
предлагает боевой рейд отдельным пунктом 4. Повтор входа сохраняет исходный режим.

trkv_combat_tester использует собственную тестовую фракцию и класс TRKV_COMBAT_TEST
с lua_ai TRKV_PATROL. В JSON задана враждебность NPCATT_KILL (10 в закреплённой BN).
weapon_override создаёт ar15 с 17 патронами 223 и штатным магазином; carry_override
EMPTY_GROUP исключает случайные запасные предметы, worn_override задаёт простую
одежду. gun/rifle имеют уровень 6. Эти параметры технические, не баланс противников.
При угрозе Lua возвращает false; прицеливание, стрельбу и прочие боевые решения
исполняет BN. Нового тактического контроллера и правил отношений USEC/BEAR здесь нет.


## Сохранение выбранного комплекта

trkv_loadouts загружается encounter при загрузке модулей. Каталог закрыт от внешней
мутации; choose принимает генератор целого броска, template разрешает только
известный ID. Combat-адаптер передаёт deployment необязательный select. Patrol-адаптер
его не использует и не расходует случайные броски на комплект.

Новый creating-slot хранит loadout до api.spawn(spec, sequence, loadout). Неправильный
тип выбора/ошибка picker возвращает selection_failed до spawn. Recovery не вызывает
select; find_slot получает сохранённый ID комплекта и отклоняет актёров с другим
тегом. ready-slot и запись участника сохраняют строковый ID, без ссылок на вещи.
Остаток патронов, износ и содержимое сохраняет сам BN. Полная атомарность не добавлена.


Каталог вариантов теперь объединяет профиль подготовки и комплект. Старые
rifle_civilian_v1/rifle_field_v1 сохраняют прежний trained-профиль, два новых ID
задают recruit с теми же двумя комплектами. Выбор полного ID остаётся единым и
сохраняется прежним полем loadout; обновления схемы storage нет. describe возвращает
новую plain-таблицу с profile/equipment/template; её изменение не меняет каталог.
JSON-классы определяют начальные значения, загрузка не повторяет randomize.


## Динамические случайные НПС

world_type получает allow_random_npcs=true по умолчанию. В проектном типе
trkv_raid_space оно false и применяется и в убежище, и в рейде. Почасовой
perhaps_add_random_npc проверяет метаданные текущего измерения перед RNG,
созданием фракции и участника. Опции мира не переопределяют запрет. Отсутствие
метаданных или невалидный world_type сохраняет прежний путь для совместимости;
проектные native/cold проверки требуют валидный собственный тип.

Явный spawn_npc_at не использует этот динамический спавнер и продолжает работать.
Не добавляем очистку чужих НПС после их появления: это уже могло бы оставить
миссии/фракции и сломать сохранённые ссылки. Остальные источники требуют своей
политики отдельно от этого флага. В тестовой установке --tests game.h получает
friend trkv_npc_spawn_probe для прямого вызова закрытого штатного спавнера;
production-установка без --tests не меняет game.h.


## Явные пулы генератора

trkv_loadouts хранит отдельно закрытый catalog полных вариантов и закрытые pools
со ссылками на варианты и весами. Идентификаторы пулов версионированы. При загрузке
модуля проверяются существование вариантов, уникальность записей и положительные
целые веса; пустой пул не допускается. describe возвращает копию описания варианта.

choose(roll, pool_id) требует явный известный ID, без default-пула. Неизвестный
пул останавливается до вызова RNG; deployment превращает ошибку выбора в
selection_failed без creating-slot и spawn. contains проверяет принадлежность
варианта заданному пулу. Боевой manifest передаёт свой pool в select(spec),
а spawn до вызова движка проверяет членство выбранного ID в этом пуле.

В storage остаётся выбранный полный ID loadout; изменения схемы нет. Ready-slot
и восстановление creating не бросают новый пул и не переклассифицируют сохранённого
участника. При последующей смене состава пулов старые ID каталога должны оставаться
разрешимыми. Новые ограничения относятся к новому созданию, а не повторной выдаче
или подмене набора существующего участника.


## Режим squad

encounter хранит закрытые manifests patrol/combat/squad. squad использует три
стабильных slot hostile_1..3, общие side=hostile_test/squad=mixed_test и три
непересекающихся маршрута в восточной части технической карты. Первому месту
задан technical_trained_rifle_v1, двум другим technical_recruit_rifle_v1. Spawn
и reconciliation используют прежний deployment, без нового способа выдачи вещей.

main принимает squad как отдельный encounter, предлагает пункт 5 терминала и
сохраняет его до перехода. Повтор входа сохраняет исходный режим. Старые режимы
не меняют состав, записанные loadout не перебрасываются. Общая строка squad не
добавляет лидерство, обмен целями, подавление или совместные манёвры.


## Ожидание занятого места создания

Новый slot сначала получает reserved и выбранный loadout. Необязательный
api.available(spec, sequence, choice) обязан быть read-only: false означает blocked,
ошибка/не-bool — placement_failed. В обоих случаях slot остаётся reserved и не
вызывает spawn; следующий ensure использует прежний choice, включая после load.
При true или отсутствии callback статус меняется на creating непосредственно перед
вызовом api.spawn. Результат с неизвестной судьбой всё ещё восстанавливается только
через find_slot; повтор создания для creating не добавлен. Ready-slot остаётся
занятым и после гибели. Схема plain storage остаётся 1; прежние ready/creating читаются.

Production available сравнивает bubble-координату первого waypoint с get_pos_ms
всех gapi.get_all_creatures (аватар, НПС и монстры). Этот запрос и привязка метода
подтверждены закреплёнными catalua_bindings_game_creatures.cpp/creature.cpp. На
blocked main не выводит ошибочное требование покинуть рейд: обычный тик проверит
место снова. Для остальных ошибок предупреждение сохраняется. Проверка не обещает
проходимости стены/мебели, она лишь предотвращает попытку создания в занятой клетке;
сам spawn_npc_at сохраняет окончательные проверки размещения. Окна записи движком
и прерывание между операциями не становятся полноценной транзакцией.


## Правило размещения НПС картой

world_type.allow_mapgen_npcs=true по умолчанию, false у trkv_raid_space. Патч
0006 применяет его в map::place_npc при force=false совместно с STATIC_NPC.
При запрете функция возвращает пустой character_id до randomize, insertion и
spawn hooks. force=true сохраняет прежний обход STATIC_NPC и доступен нашему
spawn_npc_at. Это не проверка принадлежности manifest и не общий контроль всех
путей создания НПС в движке.

world_types::infer_from_dimension(dim) извлекает прежний алгоритм cold load:
пустой ID использует default, непустой — последнее совпадение непустого
save_prefix в порядке реестра, отсутствие совпадений — default. Это не новый
алгоритм выбора самого длинного префикса. game::load вызывает тот же helper,
сохраняя прежнее поведение. Как и раньше, ID измерения должен соответствовать
save_prefix его world_type; это проверяется для проектных ID.

map::place_npc передаёт bound_dimension_, поэтому генерация чужой карты не
использует world_type игрока. Helper читает только загруженный JSON-реестр;
он не обращается к изменяемой таблице loaded_dimensions_ или текущему состоянию
игрока из worker-потока. Правила для явно заданного иного world_type при ID,
не соответствующем его save_prefix, этим решением не вводятся.


## Первое управление памятью и поиском

TRKV_PATROL каждый раз разрешает актуального member через participants.find,
передавая его в trkv_decision. Контроллер обновляет member.perception и
member.search, затем выбирает подтверждённый видимый бой / ограниченный поиск /
возврат на патруль. trkv_search отделён от adapter движения, хранит только простые
данные. Поля observed и goal предотвращают повторный запуск завершённого поиска
без нового зрительного контакта и передачу скрытой цели штатному ИИ.

Вне первого поиска модель ещё неполна: общий аварийный диспетчер угроз,
слуховые наблюдения и командные задачи не подключены. Вызовы прямого patrol
сохраняют прежний контракт; игнорирование его threat gate разрешает только
контроллер для участника с уже установленным, но потерянным зрительным контактом.


### Аварийное прерывание

После обновления perception контроллер вызывает Npc:avoid_immediate_danger()
из патча 0009. Непустой ответ означает выполненное аварийное действие;
поиск и patrol в этом решении не исполняются. Метод использует обновлённый
cache движка и не вызывает общий выбор боя. Голы/сроки поиска не обновляются
аварией. Поддержаны опасные поля и замеченная срочная взрывчатка; остальные
аварийные приоритеты требуют дальнейшего расширения.


### Анонимные слуховые события

0010 сохраняет последний уже услышанный пакет в Creature values проектного НПС.
member.hearing хранит отдельный слуховой контакт, last_event и состояние
ограниченной проверки района. NPC value переносится штатным сохранением движка;
Lua память — существующим mod_storage. Оба содержат только простые данные.

Пакет привязан к измерению и времени получения, не к live-объекту источника.
Контроллер читает его каждый ход, но повторный пакет не обновляет давность.
Проверка района следует после зрительного поиска, авария остаётся выше обоих.
Это технический канал одного последнего события; очереди, распознавание
голосов и окончательные характеристики слуха пока не реализованы.


### Подход к услышанному району

member.hearing.entry хранит простую абсолютную точку, выбранную read-only
Npc:choose_area_entry из патча 0011. Входные границы задаются только слуховым
районом; положение скрытого источника не запрашивается. Движение и повторный
выбор остаются под общим бюджетом trkv_search. entry не сохраняет Npc/Map/path
и не обновляет heard_at/expires_at. Выбор оценивает достижимость, не тактику.


### Первый боевой замысел

После аварийной проверки trkv_decision вызывает trkv_combat для trained rifle
профиля. В member.combat хранятся простые данные короткого отхода на дистанцию;
0012 оценивает/проверяет позицию, прежний move_towards исполняет шаг. Нет
указателя на цель в сохранении. При потере видимости план отменяется, после
чего применяется поиск по памяти. Перезарядка и стрельба остаются в BN.
Выбор ограничен локальными кандидатами, сроком/попытками и cooldown.


Боевой пилот дополнительно сохраняет last_now. Откат часов снимает текущую
цель и задаёт cooldown относительно нового now. Неактивный контекст и
смена на неподходящий профиль удаляют цель/cooldown/last_now до обращения
к движковым методам. Идентичность нового рейда очищает прежнюю шкалу времени.


Переходы одиночного ИИ: perception.observed фиксируется непосредственно при
законном наблюдении, а не только при получении поиска хода. Вместе со
search/hearing.observed он запрещает скрытый vanilla fallback после аварий.
member.decisions содержит ограниченную историю 8 переходов и текущую
цепочку причин отказа. Только простые значения, без координат/указателей;
повторы объединяются. Диагностика не влияет на выбор действия.

В незавершённом слуховом эпизоде combat имеет приоритет над movement.
Поднятие приоритета в том же районе не создаёт новую поисковую попытку
и не меняет исходный дедлайн. После завершения допускается новый район
по свежим шагам; отвергнутые пакеты не стоят в очереди.


Боевой goal.kind определяет политику проверки: standoff увеличивает
дистанцию, firing_lane ищет короткое смещение при перекрытой геометрической
линии на видимую цель. Оба используют один persistent controller с общими
бюджетами, аварийным приоритетом и отменой по потере контакта. Отсутствующий
kind в старых записях означает standoff. В Lua не передаются указатели
блокировщика; read-only binding возвращает только выбранную абсолютную точку.


Контроллер trkv_reload имеет приоритет после аварии, перед combat/search.
Для trained-профиля и пустого оружия с реальными боеприпасами выбирается
короткий подход к terrain cover относительно видимой выбранной угрозы.
План сохраняет position/threat/started_at/deadline/attempts/stalled, а также
raid identity и cooldown. После потери LOS допускается продолжение по свежей
зрительной памяти; новые скрытые координаты не читаются. Прикрытие проверяется
от последнего законного наблюдения, исходный threat ограничивает смещение
цели. По прибытии guarded binding вызывает BN::do_reload с реальными вещами
и затратами. Положительный результат контроллера не передаёт этот ход vanilla.
Завершение/отказ/истечение удаляет план; неизвестная схема отвергается.


Критерий terrain cover для перезарядки требует отсутствия LOS в обоих
направлениях между последним наблюдением и точкой. Исполнитель дополнительно
проверяет актуальную видимость выбранной цели. Его отказ имеет короткий
диагностический код; failure_reason сохраняется в reload-state при ошибке
исполнения и очищается новым планом/успехом/сбросом. Диагностика не даёт
разрешения перезаряжаться при открытой позиции.


Поддержание оружия не зависит от vanilla fallback: после истечения обеих
контактных памятей контроллер может вызвать guarded idle reload с реальными
патронами/ходами. Это базовая возможность trained/recruit; deliberate cover
approach остаётся только trained. Приоритет: авария → reload/maintenance →
боевой манёвр → зрительный поиск → слуховой поиск → patrol/owned wait.
Read-only evaluator прикрытия общий для выбора и explain-запроса, чтобы
диагностика не расходилась с фактической проверкой.


Reload cover не использует map::sees для двухстороннего геометрического
критерия: в закреплённой базе его reciprocal cache скрывает различия
направленных Bresenham rays. Локальный helper прямо проверяет оба
zero-slope луча штатным bresenham, включая прозрачность и вращение
транспорта. Общая видимость BN не переписана; guarded executor также
сохраняет отказ по видимой выбранной цели.


Сохранённый reload-подход повторно проверяет реальную готовность пустого
оружия/боезапаса до terrain evaluator и движения. Если задача перестала
быть актуальной, goal удаляется с no_longer_needed, failure_reason очищается,
а исходный cooldown остаётся. Это позволяет продолжить выбор другого
действия без лишнего шага к старой позиции и без нового цикла планирования.


### Локальное сообщение отряда

trkv_squad получает текущий registry через аргумент production callback;
никакая его таблица не захватывается до load. Отправитель и получатель должны
иметь одну непустую squad, одну side и текущий sequence. Отправитель заново
разрешается среди активных NPC, должен быть жив, виден получателю, на том же
этаже и не дальше 12 клеток Chebyshev. Передаётся только его личный vision
contact со status=visible, возрастом не более двух ходов, правильным dimension
и неистёкшим сроком. Это локальная абстракция указания цели, не радиосвязь.

member.squad_memory отделён от perception и hearing. contact хранит source=squad,
sender ID, копию position, исходный seen_at и expires_at=min(original, seen_at+10).
При равной свежести выбирается меньший ID для воспроизводимости. Пока сообщение
активно, новые сообщения не меняют его точку, срок или бюджет поиска. Только
личное наблюдение, истечение, смена стороны/отряда/рейда или откат времени снимают
эпизод. Свежий новый эпизод может начаться после истечения предыдущего.
Полученные сообщения не пересылаются: donor обязан иметь личный source=vision.

Поиск сообщения использует существующий bounded trkv_search с отдельным state:
после личного зрительного поиска, до слухового. Аварии и личный бой сохраняют
приоритет. Свежий report запрещает idle reload. Флаг observed запрещает hidden
vanilla fallback и после истечения сообщения; trace помечает source=squad и
action=squad_search. Никаких скрытых target coordinates, указателей, общего
всевидящего blackboard, ролей прикрытия или обхода этот этап не добавляет.


### Согласование конечных боевых точек

trkv_positions строит временный список исключений из combat.goal/reload.goal
живых видимых союзников одной side и непустой squad в пределах 12 клеток на
том же этаже. Проверяются raid identity, schema, started_at/deadline и last_now.
При создании учитываются все актуальные чужие планы; при валидации уже
сохранённого плана — только меньшие ID, чтобы конфликт после load разрешался
однозначно. Ранее существовавшая чужая точка защищена от нового выбора даже
при большем ID. Дубли обеих политик одного бойца сворачиваются.

Список содержит только временные TripointAbsMs для текущего binding-вызова,
не записывается в mod_storage и не требует нового persist schema. Registry
передаётся текущим callback, живые NPC заново разрешаются. Не читаются текущие
координаты противника и не создаётся глобальная радиосвязь. Погибший/скрытый/
далёкий союзник или истёкший план перестают резервировать точку; достигнутая
позиция дополнительно защищена обычной проверкой физической занятости BN.

0012 принимает optional excluded table четвёртым аргументом, choose_reload_cover
и reload_cover_status — третьим. Нативный scorer исключает эти абсолютные точки
до остальных проверок, поэтому исходные оценки маршрута, дистанции, опасных
полей, линии огня и прикрытия сохраняются. Поиск альтернативы выполняет тот же
нативный selector, а не Lua-перебор с ослабленной committed-политикой.
При reload-конфликте explain возвращает reserved_cover. Нет резервирования
всего пути, клеток вокруг позиции, гарантии прикрытия огнём или обхода.


### Согласование проверки сообщения

trkv_squad перед началом/продолжением report search учитывает планы живых
видимых бойцов той же side/squad, на том же этаже в пределах 12 клеток.
Требуется тот же sender и точная position, текущие identity и исходные сроки.
Непроверенные соседние точки и сообщения других источников не объединяются.
Если видимый боец с меньшим ID уже выполняет поиск, текущий боец тратит 100
moves на wait_for_investigator без движения/новых попыток. waiting_for содержит
только ID. При гибели, потере локальной связи, исчерпании попыток/застревании
или отмене peer-плана ожидание прекращается; исходный TTL сообщения остаётся.
Арбитраж сходится после обновления участников, а не гарантирует единственного
движущегося бойца до первого обмена намерениями в этом ходе.

Личное достижение report-точки записывает checked_at. Свежий отчёт от самого
проверявшего бойца может завершить дублирующий поиск: checked_at должен быть
не раньше полученного снимка и не в будущем. finished_by — простой ID;
checked_by_squad не пересылается как доказательство собственной проверки.
Повторный tick не расходует ещё один ход подтверждения. Это посещение точки,
не гарантия отсутствия врагов и не зачистка помещения. TTL и поисковый бюджет
не продлеваются. Аварии/личный контакт по-прежнему выше координации; ожидание
не обещает, что боец ведёт огонь на прикрытие.
