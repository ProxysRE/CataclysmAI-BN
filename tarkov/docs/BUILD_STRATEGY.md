# Собственная сборка или устанавливаемый мод

Рекомендация от 20 октября 2026. Вопрос пользователя о формате проекта не считается
решением немедленно переносить весь контент в core или начинать отдельную ветку движка.

## Рекомендуемая организация

Проект может распространяться единой сборкой BN со встроенным рейдовым режимом.
Внутри сборки контент остаётся самостоятельным модулем JSON/Lua. Собственные патчи
C++ добавляются, когда нужное поведение требует изменения движка. Это совместимые
способы организации: отдельный продукт не требует складывать все данные в core.

Перенос JSON из data/mods в основные данные не расширяет Lua API и не меняет
алгоритмы НПС, область симуляции или формат сохранений. Для наших задач преимущества
собственной сборки связаны с возможностью менять эти системы и поставлять точную
проверенную версию, а не с расположением файлов.

| Задача | Первое место реализации |
|---|---|
| Локации, добыча, наборы экипировки, классы НПС | Данные модуля JSON |
| Управление рейдом и доступные события | Lua модуля |
| Недоступное действие НПС или сигнал движка | Узкий binding/событие C++ с тестом |
| Изменение самого выбора действий и боевых правил | Патч C++, если существующий API не покрывает цель |
| Специальный интерфейс и запуск режима | Отдельная задача сборки/UI после готовности механик |

В изученном BN класс НПС может подключить lua_ai; возврат true перехватывает ход,
false/nil отдаёт выбор штатному ИИ. Это позволяет начать опыт с патрулём и штатным
боем без переписывания всей системы. Подробнее и точные исходники — NPC_SPIKE.md.
Прямой вызов нужной боевой операции через текущий набор bindings не следует
предполагать доступным: отсутствие интерфейса сначала проверяется отдельным опытом.

## Цена собственной сборки

- Мы собираем и выпускаем Windows executable, а не только набор файлов мода.
- Мы отвечаем за совместимость собственных сохранений и миграции наших изменений.
- Обновление основы BN становится управляемым переносом: сравнение, разрешение
  конфликтов и повтор проверок. Закреплённую базу первого слоя пока не меняем.
- Изменения движка должны быть отделимы от контента и чужих проектов репозитория.

Первый production-патч C++ — `patches/0001-restore-bounds-to-target-dimension.patch`.
Холодная загрузка воспроизвела потерю границ рейда: unserialize направлял pocket_info
в прежний буфер m до переключения измерения. Патч выбирает буфер по сохраняемому ID;
формат сохранения не меняется. Installer применяет его с --tests и без этого флага.
Игровая проверка исправления ещё ожидается; Windows-сборка с ним пока не подтверждена.
Тестовый overlay остаётся отдельным от этого production-изменения.
Следующий переход к собственной сборке не отменяет и не переписывает текущий
контроллер рейдов. Для каждого патча записываем воспроизводимый пробел, контракт
изменения и проверку результата. Разработку противников не начинаем до закрытия
первого слоя механики и сохранности вещей.
