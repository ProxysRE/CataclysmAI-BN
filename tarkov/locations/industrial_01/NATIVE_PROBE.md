# Изолированная проверка генерации настоящим BN

Подготовлена 25.10.2026. **C++ ещё не скомпилирован, native-результата нет.**
В локальном контейнере отсутствуют CMake/Ninja и требуемый современный компилятор.
Попытка `apt-get update` завершилась ошибками `setgroups`/`seteuid`: зависимости
не установлены. Ошибка окружения не является успешной проверкой карты.

Позднее запущен отдельный `.github/workflows/tarkov-locations.yml`:
[прогон 40187454931](https://github.com/ProxysRE/CataclysmAI-BN/actions/runs/40187454931).
Статические проверки, зависимости, установка и CMake configure прошли;
на момент записи идёт компиляция. Core и его workflows остаются отдельными.

## Что проверит probe

Один testcase `[trkv_locations]` создаёт отдельный временный набор mapbuffer /
overmapbuffer в одноразовом мире тестового executable. Все девять overmap IDs
выставляются до генерации, затем вызывается настоящий `mapgen_constructor::generate`.
Для каждой из 5184 клеток сверяются terrain/furniture с исходным JSON. Это проверка
интерпретации карты движком, включая ориентацию и раскладку, а не подмена генерации
ручной установкой ожидаемых клеток.

Дополнительно проверяются отсутствие ловушек, предметов и транспорта, пустые
списки спавна монстров и поля во всех 36 подкартах, отсутствие overmap NPC.
Из фактического `tile.passable()` собирается четырёхсвязный граф: все основные
и запасные старты должны достигать обоих выходов и восьми POI при закрытых
дверях. Отдельно исключаются западная и центрально-восточная части для проверки
двух независимых продольных маршрутов. Сверяется исходная мощность лампы BN,
**но световой кэш игры этим не проверяется**.

Не проверяет: перемещение настоящего НПС/аватара, время действий, открывание
дверей, игровой LOS стартов, работу света и крыш, прострелы, сохранения и рейдовый
жизненный цикл. Подключения к core, новых API и production-патчей нет.

## Установка и сборка

Нужен отдельный checkout BN на точном SHA из ТЗ и среда сборки проекта.
Не использовать пользовательские сохранения. До установки прочитать `AGENTS.md`
BN; при новых изменениях источником правил остаётся закреплённая база.

Из корня репозитория проекта:

```sh
python tarkov/tools/locations/install_native_probe.py /path/to/pinned-bn
```

Устанавливаются ровно три пути:

- `data/mods/trkv_locations_dev/`;
- `tests/trkv_location_constructor_test.cpp`;
- `tests/trkv_location_fixture.inc` — снимок ожидаемого ввода из текущих JSON.

Установщик проверяет HEAD, не перезаписывает существующие пути и откатывает
только собственные новые файлы при ошибке. Обновление установленного теста
производится в новом checkout либо после явного удаления этих трёх путей.
Существующие исходники, тестовый main и CMakeLists не изменяются.

После установки необходимо повторно выполнить CMake configure: список `tests/*.cpp`
собирается на этом этапе. На Linux использовать параметры зависимости/компилятора
из существующего `.github/workflows/tarkov-dev01.yml`, но **не запускать его installer
core и не включать `trkv_raid_core`**. Собрать и игровой executable, и `cata_test`.
На Windows использовать отдельную сборку с `cata_test-tiles` и игровым executable,
с сохранением закреплённого BN и необходимых зависимостей из Windows workflow.
Существующие workflows core не меняются; новый отдельный workflow конструктора
устанавливает и запускает этот probe на Linux. Windows-проверка пока не добавлена.

При выключенной локализации нужен `LANGUAGES=none`; `LOCALIZE=OFF` недостаточно.
Дополнительные требования сборки — в документах BN и workflow, их наличие
этот документ не подменяет. Проверка данных установленного мода выполняется
игровым executable `--check-mods trkv_locations_dev` с отдельным временным userdir.
`check_bn_data.py` для уже установленного probe применять не нужно: он намеренно
отказывается перезаписывать существующий каталог мода.

## Запуск

```sh
python tarkov/tools/locations/run_native_probe.py --bn /path/to/pinned-bn --exe /path/to/cata_test --output /path/to/location-native-logs
```

На Windows передать путь `cata_test-tiles.exe`. При необходимости использовать
подходящий SDL backend сборочного окружения, как в существующем workflow.

По умолчанию запускаются три отдельных процесса с seeds 20261025/20261026/20261027.
Каждый получает собственный `--user-dir=.../user`. Это важное ограничение:
BN test_main удаляет содержимое своего userdir при инициализации. Runner никогда
не подставляет туда каталог пользовательского мира.

Перед каждым запуском старый XML удаляется. Требуются успешный код процесса,
свежий JUnit и ровно один успешный testcase с точным именем. Пустой, чужой,
пропущенный или неуспешный тест отклоняется. Receipt создаётся только после всех
успешных процессов; прежний receipt удаляется ещё до запуска.

Хеши executable/ввода/теста/отчётов связывают результат с проверяемыми файлами.
Происхождение executable из этих исходников должен гарантировать сборочный
pipeline: само совпадение HEAD исходников этого не доказывает.

## Проверки протокола без BN

```sh
python tarkov/tests/locations/native_probe_protocol_test.py -v
```

Семь тестов прошли локально: три изолированных процесса, защита существующей
установки, отказ изменённому моду, старому XML/receipt, аварии даже с корректным
XML, ошибочным/пустым/пропущенным JUnit, откат установки при ошибке диска.
В этих тестах запуск executable подменён; они **не дают native-доказательства**.
